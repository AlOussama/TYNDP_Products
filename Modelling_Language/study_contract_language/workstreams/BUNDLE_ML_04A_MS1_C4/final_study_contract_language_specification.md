# General Energy-System Study Contract Language — research specification C4
Status: NON-NORMATIVE / RESEARCH ONLY; OWNER_TBD. Research specification release C4.0, not a wire-schema change. M3-Hybrid; see final_architecture_decision.md. This is the language specification, not an optimization-model generator.

## 1. Purpose and scope
A study contract states the external scientific obligations that participating models, data sources and evaluation procedures must meet. A study author defines the question, system boundary, exogenous context, admissible variations, methods, outputs and evidence. A model provider supplies a typed projection and required witnesses; an evaluator assesses evidence. Different internal model formulations, solver algorithms, data structures and software architectures remain possible. A contract is not an assertion that the real model meets it. CBA and IoSN are study profiles, not language primitives.

## 2. External obligations versus executable model languages
The language is descriptive and verification-oriented. Native mathematics expresses predicates and finite calculations over declared data, observed traces and candidate supports. Internal optimization variables, objective selection by a solver, model assembly and execution are outside the contract language. An observable may project a model variable, but the variable's internal formulation is not prescribed. A missing witness or unavailable data is not zero or proof. No specific backend is required.

## 3. Architecture
Native mathspec canonical specification and public Program are the sole mathematical authority, pinned to 5f1464c334c1012cdee2947d4d55b4d1d6bef40a. The outer typed contract layer adds only semantic information that is not native mathspec: physical quantities, subject identity, normative scope, authority, data binding, chronology, information, methods, composition, comparison and evidence. It refers to native expression or predicate identities rather than duplicating their AST. Legacy M0 stays a frozen reference, M2 remains bounded migration. Finite evaluation is a consumer of native Program; it is not a second language authority.

## 4. Abstract syntax and metamodel
The root Definition D=(study, frame, slots, sources, requirements); Instance I=(definition_ref, slot bindings, events, disclosures, data receipts, context data, reports). Package=(D,I?,receipt). Frame includes domains, scopes, components, ports, referents, observables, inputs, outputs, relations, authorities, variations, chronologies, information sets, slots, processes, comparisons, relation domains, context fields, report requests. A slot references a native mathematical package, profile, source, typed bindings, assertions, policies, states, comparisons, verification and optional ledger. Requirements declare boundaries, data contracts, process roles, normativity, model declarations, comparisons and time policies. Qualified identifiers are unique within typed registries; every reference resolves to the required kind. All nine C19 core-role distinctions C1–C9 remain, without requiring nine unrelated classes. See final_metamodel.json and final_schema.json for exact existing versions. Structural schema validity is necessary, not sufficient for semantic admission.

## 5. Concrete authoring
A and B encode the same typed structural information; the wire envelope is c3-authoring-0.1. A uses the R1 lexer plus structural objects/lists, not the R1 mathematical AST. B is strict JSON. Grammar sketch: Source ::= study_contract quoted-version { definition Object instance Object }; Object ::= { (Key : Value ;)* }; Value ::= Object | List | QuotedString | Integer | true | false | null. Keys may be quoted or bare accepted names; List has comma-separated values. Duplicate keys, trailing source, unsupported literal floats and incorrect envelope versions reject. Exact quantities are strings or integers at their declared typed positions. For example, a structural illustration (not a complete admitted contract) is:
```
study_contract "c3-authoring-0.1" {
 definition { "schema": "c2-closure-definition-0.2"; }
 instance { "schema": "c2-closure-instance-0.2"; }
}
```
The corresponding B has keys schema, definition and instance, with the same nested fields. Native expression source uses mathspec grammar, not the outer object grammar. Full admitted research reference examples and source pins are in reference_library. A/B examples share one authored design; they are not independent human authoring.

## 6. Native mathematical subset
The versioned allowlist in supported_mathspec_subset.json is normative only for this research candidate's admission scope, not for upstream mathspec. Allowed sections: version, description, dimensions, relations, parameters, expressions, conditions, assumptions. Native expression nodes: Constant, ParameterReference, ExpressionReference, Negate, Add, Multiply, Divide, Power, Sum, Join, Translate, WindowSum, Cases. Conditions and finite supported dispatch are constrained by the exact manifest; static admission does not imply runtime support for all native constructs. Domain values and typed roles bind external parameters; no raw custom AST, arbitrary user function or solver-only constructs. Native arithmetic uses exact finite support with the validated quantity algebra.

## 7. Physical types and dimensions
A quantity type binds physical kind, unit/dimension, carrier, reference basis, sign convention, direction and temporal support. Type compatibility requires the intended carrier/basis and semantics, not just numerical dimension. MW and MWh differ by time integration, kg and MWh_H2_LHV by an explicit justified heating value, price bases and periods by explicit conversion. Unit conversion is admitted only by the registry and typed exact source-bound rule. A signed injection value does not become an unsigned magnitude without a scoped transformation, e.g. charging magnitude=-injection for p<=0, with raw source preserved. Unknown units/ambiguous signs reject or block; no inference from name. Numeric and categorical context supports are typed separately.

## 8. Components, ports and boundaries
A component is a typed referent with externally observed properties and ports. A port has stable identity, subject component, quantity, direction, axes and authority. A link connects compatible typed ports: carrier, units/basis, sign/direction, temporal support and topology roles are explicit. A frame defines included subjects, environment, spatial/functional scopes and relations. External obligations can express nodal balance, converter transfer, mass/energy conservation and service, but the contract does not fix a model's internal state or formulation. Source-coordinate translations for frozen research records are adapters, not domain language rules.

## 9. External obligations
An assertion binds a native predicate identity to modality, semantic role, scope, ordered binders, guard, assumptions and authority refs. MUST/MUST_NOT/MAY have different semantics; permission never supplies evidence. Data assumptions are distinct from safety, service and capability guarantees. Assertion domains and dependencies must be fully typed; coordinate restrictions must be explicit and must not hide mandatory support. Observables include typed identity or native derived projection with actual subject dependency. Missing required domain or incompatible projection rejects.

## 10. Assume–Guarantee
For each coordinate of the declared applicable support, evaluate assumptions and guard with strong Kleene three-valued logic. FALSE excludes the coordinate under the declared applicability; UNKNOWN blocks a positive assessment, TRUE activates the guarantee. No hidden default true or vacuous proof. Safety/prohibition quantify universally over relevant support. Capability specifies FORALL request EXISTS response over an explicit finite response set. Service additionally requires actual response witnesses per applicable request, tied to the source/snapshot. A finite observed true is not a universal behavioral theorem. Conflicting identical unconditional must/prohibition rejects; arbitrary global guard consistency is not established.

## 11. Data and method contracts
DataContract specifies immutable source, license/access, snapshot reproducibility, quality and missing-data policy, typed conversion where applicable. Hash matching establishes identity, not external authenticity or legal approval. MethodProfile provides native mathematics, typed signature, input roles, parameter ranges, weight/probability policy, pair policy, output/intermediate partition, versioned source and approval state. Bind a reusable definition to a separately pinned instance. Slot dependency edges must agree with actual producer/consumer bindings; cycle, duplicate producer or stale digest rejects. No hardcoded discounting method in the generic validator. Contribution ledger retains exact source-event and coordinate identity with explicit DISJOINT/ALLOW_REUSE policy and coverage; numeric agreement alone cannot verify aggregation.

## 12. Time, scenario and information
Domains declare finite labels and explicit order where semantic. Chronology defines positive interval durations and endpoints; stage is distinct from physical time. Translate/window boundaries are explicit. State endpoints and cyclic equality are explicit typed predicates. Scenarios have declared probability/weight roles, supports and information partitions with valid refinement; nonanticipativity compares actual pre-revelation decisions within each information cell. No hidden default duration, calendar or DST conversion; equal labels do not imply equal temporal meaning.

## 13. Variation and comparison
VariationPolicy defines permitted alternatives, scope, disclosure and required source/evidence. Internal coordinates, solver or form may vary subject to contract. Aggregation, integer granularity and approximation are permitted only with explicit conditions. ComparisonContract defines distinct model identities, same study context, shared typed observables, snapshot and exogenous data, counterfactual differences, tolerance, selection, sensitivity and decision threshold. Pair exogeneity checks actual bound data identities for declared fields, not just equal arbitrary tokens. Finite selection requires membership (EXISTS) and ordering (FORALL) on the same complete support; ties admitted if the rule permits. A same-KPI result does not imply E4 or independently verified conformance.

## 14. CSNF
Semantic normal form comprises the native canonical mathematical package and deterministic outer contract projection. Typed unordered registries may sort by qualified ID; preserve ordered chronology, axes, quantifier order, event multiplicities and source/authority distinctions. Definition and instance are independently pinned; native identity, MethodProfile identity, source identity, semantic identity and audit identity are not interchangeable. Reimport recomputes bytes and receipt. See canonical_normal_form_specification.md.

## 15. Governance and provenance
Normativity, source authority, owner/decision state and evidence are separate. REQUIRED versus PERMITTED and OWNER_TBD versus approval are not equivalent. Research-only override is scoped and explicitly authorized in a separately pinned authorization record, not normative owner approval. Preserve exact source bytes, immutable refs, versions, source hashes and origin links. Sources with same statement can remain separately authoritative; never erase their provenance. OWNER_TBD remains unresolved.

## 16. Verification and evidence
EvidenceRequest names subject, oracle, level, scope and expected kind. Result records actual execution and observed outcome with input and source pins, run and diagnostics. NOT_EXECUTED, BLOCKED, INCONCLUSIVE, PASS and FAIL must not be conflated. Finite truth and static validity are evidence levels, never automatic general conformance. Structured diagnostic reports code, actual validation-object path, rule ID/pinned source, reason, subject, source references and status. Unknown internal exceptions remain internal blockers and are not expected-rejection successes.

## 17. Normalization
R00–R13 remain the original C19 rule identities and preconditions in normalization_rules.md. Native mathspec performs mathematical canonicalization; the outer projection applies only classified sound rewrites. R06 unit conversion, R07 duration, R08 port orientation and R09 authority preserve semantics and evidence. R10 explicit composition is not a canonical rewrite. R11 defaults require explicit typed authorization; R12 observable semantics and R13 evidence status preserved. Deterministic output under fixed versions and tested fragment does not prove a global Church–Rosser property.

## 18. Equivalence
E1 syntactic normalisation equivalence; E2 contract semantic equivalence (obligation vs audit identity); E3 observed projection equivalence under declared support/selection/tolerance; E4 projected feasible-set and objective equivalence under explicit hypotheses; E5 permitted structural non-equivalence with external conformance, authorized variation and required evidence. Original C19 definitions reproduced in equivalence_E1_E5_assessment.md with separate evidence. No promotion E1→E2→E3→E4/E5 by default.

## 19. Extension and composition
Extend profiles, typed referent kinds, declarations, relations and supported rules only within admitted signatures, registries and versioned authority. Generic typed configurations are preferable to new primitives. Exact disjoint slot replacement requires immutable base, old/new slot hashes, explicitly listed native expression changes and separate research authorization. Re-admit protected interface, native predicates, sources, obligations, evidence and instance bindings. Stale authorization, overlapping targets or implicit override reject. New unsupported math operators require upstream native support and a bounded typed-admission decision, not a parallel AST.

## 20. Language boundaries
Finite exact fragment, not arbitrary mathematical logic, unrestricted sparse domains/temporal transformations, global consistency solver, executable full optimization model, generalized model-to-model equivalence proof, real model certification or normative methodology. Source authenticity, complete real data coverage, independent human usability and general extension/migration remain separately assessed. CBA P5 and RC examples are synthetic projections; full IoSN and CBA normative coverage are not established. Language readiness depends on gate_status.json; existence of this document is not a final acceptance decision.
