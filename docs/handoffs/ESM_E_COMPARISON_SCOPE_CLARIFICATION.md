## 1. Corrected scientific question

Which of the four core ecosystem families — **GEMS, Antares, PLEXOS and PyPSA-based solutions** — can implement the European/national/regional planning requirements most appropriately, with which mathematical model depth, data coverage, interoperability, reproducibility, numerical performance and extension effort?

Do not select a primary general optimizer, canonical modelling language, universal exchange format or federated production architecture before this comparison. ESM-E's earlier recommendation of PyPSA/Linopy as primary is only a hypothesis. The GEMS-first option must be assessed at equal depth. PLEXOS is a first-class comparison arm, not a peripheral reference. Existing eGon/eDisGo/FlexPlan and TYNDP_Products M2 reviews are useful supplementary evidence for coupling and physical planning, not additional primary contenders or replacements for the core comparison.

| Family | Distinct executable/model variants to compare | Object of comparison |
|---|---|---|
| GEMS | GEMS language/libraries; GemsPy; Antares Modeler standalone | expressive declarative LP/MILP modelling, time/scenario/port semantics, reuse of component equations, authoring, generated optimization problem, interpreter parity |
| Antares | classic antares-solver; hybrid; Xpansion annual/trajectory | built-in operational/Monte Carlo adequacy and stochastic investment models, legacy data contracts, integration with GEMS |
| PLEXOS | LT Plan / PASA / medium- and short-term scheduling as applicable; actual TYNDP electricity/H2 profile | integrated proprietary market and investment model, asset libraries, phase transitions, data/API, benchmark reference; distinguish generic software capabilities from activated official study configuration |
| PyPSA | Core + Linopy; PyPSA-Eur; PyPSA-DE; Open-TYNDP 2024 and 2026 profiles | native algebraic component model, concrete sector libraries, optimization modes, official-data workflow, benchmark parity, custom constraints |
| Interfaces (cross-cutting) | PyPSA→GEMS, GEMS→PyPSA, GEMS→Linopy, Antares legacy→GEMS, PLEXOS XML/API→canonical case and reverse | separate mapping/compilation/execution tests; not an additional energy-system engine |
| Supplementary | TYNDP_Products, eGon-data/eDisGo, FlexPlan, AC/DSO/gas/dynamic tools | physical network and regional coupling gaps only; no presumption of replacement or automatic integration |

## 3. GEMS ↔ PyPSA: independent interoperability scope

The existing official [PyPSA-to-GEMS-Converter](https://github.com/AntaresSimulatorTeam/PyPSA-to-GEMS-Converter/tree/44d73886cf17040550508e88735e451e59a06d5c) maps an unoptimized PyPSA Network to a GEMS study folder. B G01–G12 still apply. The verified [GemsPy optimization builder](https://github.com/AntaresSimulatorTeam/GemsPy/blob/77100798fd4cc7fbb2889fc278b257d58c1f08bb/src/gems_runner/simulation/optimization.py) builds a Linopy model from GEMS definitions. A Linopy optimization model is **not** a PyPSA Network.

| Interface route | Status | Testable hypothesis |
|---|---|---|
| PyPSA→GEMS→GemsPy | existing subset, C/T/limited CI; not general lossless | equivalent LP/MILP variables, constraints, objective, capacities and dispatch in admitted model subset |
| PyPSA→GEMS→Antares Modeler/Xpansion | existing subset with specific mode/solver and decomposition requirements; B | same semantics plus scenario weighting, shared investment and correct decomposition |
| GEMS→Linopy (GemsPy) | implemented C; not a new converter | independent direct GEMS vs same PyPSA model can solve matched optimization problems via a common backend |
| GEMS→PyPSA Network | **UNVERIFIED** existing public reverse converter; feasible **research/adapter hypothesis** only for recognizable model patterns | match known bus/load/generator/line/link/store models by declared identities, equations and units; preserve port graph, cost basis, domains, time/s/snapshot weights and topology |
| General GEMS→PyPSA+custom Linopy constraints | MODEL_EXTENSION/adapter hypothesis, not implemented here | declaratively represent unsupported components using custom variables/constraints only where exact correspondence can be proven; retain external GEMS model if not representable |
| Roundtrip GEMS→PyPSA→GEMS or reverse | HOLD | structural and numerical equivalence modulo declared auxiliary variables; reject unsupported/lost semantics; inverse not guaranteed after lossy mapping |
| PLEXOS XML/API↔canonical case | candidate adapter, D and inspected API docs; no universal converter proven | pin property/collection schema; scenarios, bands, memberships, unit constraints and phase controls; preserve input and output metadata |

An arbitrary GEMS model may have component-specific variables, port interactions and time/scenario dependence beyond native PyPSA component schemas. A reverse mapping cannot be inferred merely because both use Linopy. Investigate (i) direct mapping known library IDs; (ii) exact Linopy augmentation; (iii) rejection/external execution for nonrepresentable models. Compare objective and feasible set after removing legitimate auxiliary variables, not just file format or scalar objective. Explicit negative cases: multiport with shared activity, asymmetric storage, nonzero PST, custom budget, investment periods, scenario-shared variables, nonuniform time/weights, inactive assets. No requirement to build a converter if a direct independent model solves the intended comparison more transparently.
